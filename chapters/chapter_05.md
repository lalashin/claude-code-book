# 챕터 5: 진짜 프로젝트에 투입하기 — 코드베이스를 이해하고 수정하기

## 이 챕터에서 배울 것

여기까지 왔다면 여러분은 이미 AI에게 파일을 만들게 하고, 작은 웹페이지나 스크립트를 직접 만들어 실행해봤습니다. 그건 **내가 처음부터 만든, 내가 다 아는 작은 결과물**이었습니다.

이 챕터부터는 무대가 바뀝니다.

이제 여러분 앞에는 **남이 만든, 여러분도 잘 모르는 큰 코드 더미**가 놓입니다. 수십 개의 파일, 처음 보는 폴더 구조, 어디서 무엇이 동작하는지 한눈에 들어오지 않는 진짜 프로젝트요. 회사에서 인계받은 코드, 인터넷에서 내려받은 오픈소스, 몇 달 전의 내가 만들어놓고 까먹은 프로젝트가 모두 여기에 해당합니다.

> **이 챕터가 입문과 중급의 분기점입니다.** 지금까지는 "AI가 코드를 잘 짜주는가"가 관건이었습니다. 지금부터는 다릅니다. **"AI에게 이 프로젝트를 얼마나 잘 파악시키는가", 즉 맥락(context)을 주는 능력이 곧 여러분의 실력이 됩니다.** 코드를 직접 읽고 쓰는 일은 여전히 AI가 합니다. 여러분이 잘해야 하는 건 AI를 올바른 방향으로 안내하는 일입니다.

이 챕터를 끝까지 따라 하면 여러분은 이렇게 할 수 있습니다.

- 처음 보는 프로젝트를 AI에게 탐색·요약시켜 5분 만에 전체 그림을 파악한다
- "로그인 버튼 색을 바꿔줘" 같은 요청을, 어느 파일을 고쳐야 하는지 몰라도 AI가 알아서 찾아 처리하게 한다
- 큰 변경은 곧바로 시키지 않고 **계획(Plan)을 먼저 받아본 뒤** 단계별로 승인하며 안전하게 진행한다
- 버그를 만났을 때 **재현 → 원인 파악 → 수정 → 검증**의 디버깅 루프를 AI와 함께 돈다
- `CLAUDE.md` 파일로 프로젝트의 규칙과 맥락을 AI에게 **영구히 기억**시킨다

코드를 한 줄도 직접 읽지 못해도 괜찮습니다. 이 챕터의 모든 코드 조각에는 한국어 설명이 붙어 있어, 코드 자체를 못 읽어도 **흐름**은 따라올 수 있게 했습니다.

## 5.1 시작하기 전에 — AI에게 요청하는 기본 패턴 (30초 복습)

본격적으로 들어가기 전에, 중급 작업 내내 반복해서 쓸 **요청의 기본 골격**을 반 페이지로 압축해 드립니다. 챕터 2를 읽은 분은 복습이고, 중급부터 합류한 분은 여기만 기억하면 됩니다.

좋은 요청은 거의 항상 다음 세 가지를 담습니다.

```
[맥락]  지금 어떤 상황인가  →  "이건 React로 만든 할 일 앱이야"
[목표]  무엇을 원하는가     →  "완료 버튼을 누르면 줄이 그어지게 하고 싶어"
[제약]  무엇을 지켜야 하나   →  "기존 디자인은 건드리지 말고, CSS만 수정해줘"
```

이 세 박자를 의식하면 AI의 적중률이 눈에 띄게 올라갑니다. 그리고 중급에서 새로 추가되는 습관이 두 가지 있습니다.

- **큰일은 계획부터 받는다.** "바로 고쳐줘" 대신 "어떻게 고칠지 계획부터 보여줘"라고 한 박자 쉬어 갑니다.
- **모르면 물어보게 한다.** "애매한 부분이 있으면 작업 전에 먼저 질문해줘"를 요청 끝에 붙이면, AI가 엉뚱한 방향으로 달려가는 걸 막을 수 있습니다.

이 두 습관이 이 챕터 전체를 관통하는 안전벨트입니다.

## 5.2 실습 환경 준비 — 모두가 같은 프로젝트로

이 챕터의 실습은 모두 **하나의 작은 샘플 프로젝트** 위에서 진행합니다. 독자마다 다른 코드를 쓰면 출력이 제각각이 되니, 환경을 통일하겠습니다.

복잡한 오픈소스를 내려받는 대신, **AI에게 실습용 미니 프로젝트를 직접 만들게** 하겠습니다. 이게 가장 확실하게 환경을 맞추는 방법입니다.

### 실습 5-1: 실습용 미니 프로젝트 생성하기

먼저 작업할 폴더를 만들고 그 안에서 Claude Code를 실행합니다.

Windows (PowerShell):
```
cd Desktop
mkdir todo-app
cd todo-app
claude
```

Mac (터미널):
```
cd ~/Desktop
mkdir todo-app
cd ~/Desktop/todo-app
claude
```

Claude Code가 켜지고 `>` 프롬프트가 보이면, 아래를 그대로 입력하세요.

```
간단한 '할 일 목록(To-Do)' 웹 앱을 만들어줘.
조건은 이래:
- HTML, CSS, JavaScript 파일을 따로 나눠서 만들어줘 (index.html, style.css, app.js)
- 할 일을 입력칸에 적고 '추가' 버튼을 누르면 목록에 추가돼야 해
- 각 할 일 옆에 '삭제' 버튼이 있어야 해
- 데이터는 브라우저 localStorage에 저장해서 새로고침해도 남아있게 해줘
- 파일을 나눠 만든 이유와 폴더 구조를 마지막에 설명해줘
```

AI가 파일 세 개를 만들고 구조를 설명해줄 것입니다.

```
다음 파일들을 생성하겠습니다.

● Write(index.html)    화면 구조 (입력칸, 추가 버튼, 목록)
● Write(style.css)     디자인 (색상, 여백, 버튼 모양)
● Write(app.js)        동작 로직 (추가, 삭제, 저장)

✓ 완료. 폴더 구조는 다음과 같습니다.

todo-app/
├── index.html   ← 브라우저로 열면 이 파일이 화면을 그립니다
├── style.css    ← 색·폰트·간격 등 보기 좋게 꾸미는 부분
└── app.js       ← 버튼을 누르면 실제로 동작하게 만드는 두뇌

index.html을 더블클릭하면 바로 실행됩니다.
```

`index.html`을 더블클릭해 브라우저로 열어보세요. 할 일을 추가하고 삭제할 수 있는 작은 앱이 떠 있을 겁니다. **이 작은 프로젝트가 이 챕터 내내 우리의 실험 대상**입니다.

> **왜 굳이 파일을 셋으로 나눴을까요?** 진짜 프로젝트는 거의 다 이렇게 **역할별로 파일이 흩어져** 있기 때문입니다. 화면 따로, 디자인 따로, 동작 따로. 이렇게 흩어진 코드 속에서 "고쳐야 할 곳"을 찾아내는 것이 바로 이 챕터의 핵심 주제입니다.

스스로 해보기: 위 요청에서 마지막 줄을 빼고 "데이터를 저장하지 말고 새로고침하면 사라지게 해줘"로 바꿔 다른 폴더에 또 하나 만들어보세요. 같은 요청이라도 제약 한 줄이 결과물을 어떻게 바꾸는지 비교해볼 수 있습니다.

## 5.3 프로젝트 전체를 파악시키기 — "이 프로젝트 설명해줘"

진짜 프로젝트를 만났을 때 가장 먼저 할 일은 **코드를 고치는 게 아니라 파악하는 것**입니다. 다행히 이건 AI가 가장 잘하는 일 중 하나입니다.

여러분이 처음 보는 프로젝트라도, AI에게 한 문장만 던지면 됩니다.

### 실습 5-2: 프로젝트 구조 설명받기

방금 만든 `todo-app` 폴더에서 Claude Code를 실행한 상태로(아니라면 `cd`로 이동 후 `claude` 실행) 다음을 입력하세요.

```
이 프로젝트의 전체 구조를 설명해줘.
- 어떤 파일들이 있고 각각 무슨 역할을 하는지
- 데이터는 어디에 어떻게 저장되는지
- 내가 '완료 표시 기능'을 추가하려면 어느 파일을 봐야 하는지
초보자도 이해할 수 있게 설명해줘.
```

AI는 먼저 스스로 파일들을 **읽어본 뒤** 답합니다.

```
프로젝트를 살펴보겠습니다.

● Read(index.html)
● Read(style.css)
● Read(app.js)

이 프로젝트는 순수 HTML/CSS/JavaScript로 만든 할 일 목록 앱입니다.

[파일 역할]
• index.html — 화면의 뼈대. 입력칸 1개, '추가' 버튼 1개,
  할 일이 쌓이는 빈 목록(<ul id="todo-list">)이 있습니다.
• style.css  — 보기 좋게 꾸미는 부분. 버튼 색, 글자 크기,
  완료된 항목에 줄을 긋는 스타일(.done)이 미리 준비돼 있네요.
• app.js     — 실제 동작. '추가' 버튼 클릭 → 목록에 추가 →
  localStorage에 저장하는 흐름을 담당합니다.

[데이터 저장]
브라우저의 localStorage에 'todos'라는 이름으로 저장됩니다.
그래서 새로고침해도 목록이 유지됩니다.

[완료 표시 기능을 추가하려면]
app.js의 renderTodos() 함수를 보세요. 여기서 각 할 일을
화면에 그립니다. 항목을 클릭하면 .done 스타일이 켜지도록
이 함수에 클릭 처리를 추가하면 됩니다. 마침 style.css에
.done 스타일이 이미 있어서 활용하기 좋습니다.
```

주목할 점이 두 가지 있습니다.

첫째, AI가 답하기 전에 `Read(...)` 줄이 먼저 나왔습니다. **AI가 추측으로 답하는 게 아니라 실제로 파일을 열어 읽고 답한다**는 증거입니다.

둘째, 마지막 문단에서 AI는 "완료 기능을 넣으려면 `app.js`의 `renderTodos()`를 보라"고 **콕 집어** 알려줬습니다. 여러분이 코드를 한 줄도 안 읽었는데도, 어디를 손대야 할지 길잡이를 얻은 겁니다. 이게 바로 다음 절에서 다룰 "맥락 수집"의 첫 단추입니다.

> **현실 팁:** 파일이 수백 개인 진짜 프로젝트에서도 똑같이 통합니다. "이 프로젝트가 무슨 일을 하는 앱인지, 핵심 폴더 3개만 골라 설명해줘"처럼 **범위를 좁혀** 물으면, AI가 방대한 코드에서도 요점만 추려줍니다.

스스로 해보기: "이 앱에서 가장 중요한 함수 하나를 골라, 그게 무슨 일을 하는지 한 문단으로 설명해줘"라고 물어보세요. AI가 코드의 심장부를 어떻게 짚어내는지 관찰해보세요.

## 5.4 AI는 어떻게 관련 파일을 스스로 찾을까 — 맥락 수집의 원리

여러분이 "로그인 버튼 색을 바꿔줘"라고 했을 때, 어느 파일의 몇 번째 줄을 고쳐야 하는지 AI가 어떻게 알까요? 폴더에 파일이 200개라면요?

비밀은 단순합니다. **AI도 우리처럼 검색합니다.** 다만 사람보다 훨씬 빠르고 지치지 않을 뿐입니다.

AI가 관련 코드를 찾는 과정은 대체로 이렇습니다.

```
1. 요청에서 단서를 뽑는다       "로그인 버튼", "색"
2. 그 단어로 코드 전체를 검색한다  login, button, color, background ...
3. 후보 파일들을 실제로 읽어본다   Read(style.css), Read(login.js) ...
4. 진짜 고칠 곳을 특정한다        style.css의 .login-btn 부분
```

이 과정을 우리가 일일이 시킬 필요는 없습니다. AI가 알아서 합니다. 우리 눈에는 작업 로그로 이렇게 비칠 뿐입니다.

```
● Search("추가" 또는 "button" 관련 코드 찾는 중...)
● Read(app.js)
● Read(index.html)
이 두 파일에서 '추가' 버튼 관련 코드를 찾았습니다.
```

여기서 중요한 교훈이 나옵니다. **AI가 검색으로 길을 찾기 때문에, 우리가 주는 단어가 곧 검색의 출발점**이라는 것입니다.

- 모호한 단어를 주면 → AI가 엉뚱한 파일을 뒤집니다. ("그거 좀 바꿔줘")
- 구체적인 단어를 주면 → AI가 정확한 곳으로 직행합니다. ("'추가' 버튼의 배경색을 파란색으로 바꿔줘")

즉, 5.1에서 말한 "맥락을 주는 능력"이란 거창한 게 아닙니다. **AI가 검색하기 좋은 단어를 던져주는 것**, 그게 절반입니다.

### 실습 5-3: 관련 파일 자동 탐색 시켜보기

`todo-app`에서 다음을 입력하세요. 어느 파일을 고쳐야 하는지 **여러분은 모른 채로** 시작합니다.

```
'추가' 버튼의 색을 초록색으로 바꿔줘.
어느 파일을 고쳐야 하는지 먼저 찾아서 알려준 다음 바꿔줘.
```

```
'추가' 버튼 관련 코드를 찾아보겠습니다.

● Read(index.html)   → 버튼의 정체 확인: <button id="add-btn">추가</button>
● Read(style.css)    → 이 버튼의 색을 정하는 부분 발견: #add-btn { background: #3b82f6 }

style.css의 #add-btn 규칙에서 배경색을 정하고 있습니다.
이 부분을 초록색으로 바꾸겠습니다.

● Edit(style.css)
  #add-btn {
-   background: #3b82f6;   (파란색)
+   background: #22c55e;   (초록색)
  }

✓ 변경 완료. 브라우저를 새로고침하면 '추가' 버튼이 초록색으로 보입니다.
```

여러분은 `style.css`가 색을 담당한다는 것도, `#add-btn`이라는 이름도 몰랐습니다. 그저 **"'추가' 버튼"이라는 구체적인 단어**를 줬을 뿐인데 AI가 검색으로 정확히 찾아냈습니다. 이것이 중급 작업의 기본 리듬입니다.

스스로 해보기: 이번엔 "할 일 글자 크기를 좀 더 크게 키워줘"라고 요청해보세요. AI가 `style.css`의 어느 부분을 어떻게 찾아 고치는지 로그를 따라가 보세요.

## 5.5 큰 변경은 계획부터 — Plan을 먼저 받고 실행하기

지금까지는 "버튼 색 바꾸기"처럼 작고 안전한 변경이었습니다. 한 군데만 고치면 끝나죠.

하지만 "**완료 체크 기능을 추가해줘**" 같은 요청은 다릅니다. 이건 화면(`index.html`)도, 동작(`app.js`)도, 저장 방식도 한꺼번에 손대야 하는 **큰 변경**입니다. 이런 걸 "바로 해줘"라고 던지면, AI가 여러 파일을 한 번에 휘저어 놓고, 결과가 마음에 안 들면 어디서부터 잘못됐는지 추적하기 어려워집니다.

그래서 중급의 핵심 안전장치가 등장합니다. **계획(Plan)을 먼저 받는 것**입니다.

> **원칙:** 변경이 파일 두 개 이상을 건드릴 것 같으면, 바로 시키지 말고 **"어떻게 할지 계획부터 보여줘"**라고 하세요. 계획을 읽고 납득한 뒤에 실행을 승인하면, 사고를 미리 막을 수 있습니다. 운전대를 AI에게 넘기기 전에 **목적지와 경로를 먼저 확인**하는 셈입니다.

### Plan 모드란?

Claude Code에는 **계획 먼저, 실행 나중**을 강제하는 전용 모드가 있습니다. 이 모드에서는 AI가 코드를 **읽고 분석은 하지만, 실제 파일은 건드리지 않은 채** 계획만 세워 보여줍니다. 여러분이 승인해야 비로소 코드를 고치기 시작합니다.

켜는 방법은 두 가지입니다.

- **Shift + Tab**을 눌러 모드를 전환합니다. (누를 때마다 모드가 순환하며, `plan mode`라고 표시되는 상태로 맞춥니다)
- 또는 그냥 요청 문장에 **"실행하지 말고 계획만 세워서 보여줘"**라고 적어도 됩니다.

처음엔 후자가 쉽습니다. 문장으로 부탁하는 방식으로 해보겠습니다.

### 실습 5-4: 큰 기능을 계획부터 받아 단계별로 승인하기

`todo-app`에서 다음을 입력하세요.

```
각 할 일을 클릭하면 '완료' 표시(줄 긋기)가 되는 기능을 추가하고 싶어.
바로 고치지 말고, 어떤 파일을 어떻게 바꿀지 계획부터 단계별로 세워서 보여줘.
애매한 부분이 있으면 먼저 질문해줘.
```

AI는 코드를 읽어본 뒤, **고치지 않고 계획만** 내놓습니다.

```
코드를 살펴봤습니다. 계획을 세우기 전에 한 가지 확인할게요.

❓ 완료된 할 일을 다시 클릭하면 '완료 취소'(줄 긋기 해제)도
   되게 할까요? 보통 그렇게 많이 만듭니다.

(사용자: 응, 다시 누르면 취소되게 해줘)

좋습니다. 다음 계획으로 진행하겠습니다.

──────────── 변경 계획 ────────────
[1단계] app.js — renderTodos() 함수에 클릭 이벤트 추가
        각 할 일 항목을 클릭하면 'done' 상태가 켜지고/꺼지게 함

[2단계] app.js — 할 일 데이터에 done: true/false 항목 추가
        localStorage에 완료 여부까지 함께 저장

[3단계] (style.css는 이미 .done 줄긋기 스타일이 있어 수정 불필요)
────────────────────────────────────

위 계획대로 진행할까요?
  1. 네, 진행하세요
  2. 아니요, 수정할게요
```

여기서 일어난 일을 곱씹어 봅시다.

1. AI가 **먼저 질문**했습니다. "완료 취소도 되게 할까요?" — 우리가 "애매하면 물어봐"라고 했기 때문입니다. 이 질문 하나로 나중에 다시 고치는 수고를 덜었습니다.
2. AI가 **고치기 전에 계획을 펼쳐** 보였습니다. 우리는 3단계 중 `style.css`는 손댈 필요가 없다는 것까지 미리 알 수 있습니다.
3. 우리가 **승인 버튼을 누르기 전까지 코드는 그대로**입니다. 계획이 마음에 안 들면 "2번"을 눌러 방향을 틀면 됩니다.

`1`을 눌러 승인하면, 그제야 AI가 실제 수정을 시작합니다.

```
계획대로 진행하겠습니다.

● Edit(app.js)   renderTodos()에 클릭 시 done 토글 처리 추가
● Edit(app.js)   저장 데이터에 done 항목 포함

✓ 완료. 브라우저를 새로고침한 뒤 할 일을 클릭해보세요.
  한 번 누르면 줄이 그어지고, 다시 누르면 풀립니다.
```

브라우저에서 할 일을 클릭해보세요. 줄이 그어졌다 풀렸다 합니다. **계획 → 승인 → 실행**의 한 사이클을 완주한 겁니다.

> **작은 단위로 쪼개기.** 만약 한 기능이 너무 크면(예: "회원가입, 로그인, 마이페이지를 다 만들어줘"), 계획을 받은 다음 **"1단계만 먼저 하고 멈춰줘. 확인하고 다음 단계 시킬게"**라고 하세요. 큰 변경을 작은 승인들로 잘게 나누면, 매 단계마다 동작을 확인할 수 있어 사고가 나도 피해가 작습니다. 이것이 큰 변경을 안전하게 다루는 핵심 습관입니다.

스스로 해보기: "완료된 할 일만 모아서 한꺼번에 지우는 '완료 항목 모두 삭제' 버튼을 추가해줘. 계획부터 보여주고, 1단계씩 승인받으며 진행해줘"라고 요청해보세요. 계획을 쪼개 승인하는 흐름을 직접 운전해보는 겁니다.

## 5.6 버그를 잡는 법 — 재현·진단·수정·검증의 디버깅 루프

진짜 프로젝트에서 가장 자주 마주치는 일은 새 기능 추가가 아니라 **버그 잡기**입니다. 멀쩡히 돌던 게 갑자기 안 되거나, 처음부터 뭔가 어긋나 있죠.

버그를 AI와 잡을 때는 정해진 **루프**가 있습니다. 이 순서를 지키는 것만으로 해결률이 크게 올라갑니다.

```
① 재현    버그를 똑같이 다시 일으킨다 (어떻게 하면 터지는가)
② 진단    원인을 찾는다 (왜 터지는가)
③ 수정    코드를 고친다 (어떻게 막는가)
④ 검증    정말 고쳐졌는지 확인한다 (이제 안 터지는가)
```

핵심은 **①번 재현 정보를 AI에게 최대한 정확히 넘기는 것**입니다. "안 돼요"가 아니라 "이렇게 하면 이런 에러가 떠요"라고요. 에러 메시지는 짜증나는 빨간 글씨가 아니라, **AI에게 주는 가장 값진 단서**입니다.

### 실습 5-5: 버그를 심고, 재현하고, 함께 잡기

학습을 위해 일부러 버그를 하나 심겠습니다. 먼저 AI에게 버그를 만들어달라고 하겠습니다(실전에서는 이미 버그가 있는 상태에서 시작하겠지만, 여기선 재현 가능한 상황을 만들기 위함입니다).

```
공부를 위해 일부러 버그를 하나 심어줘.
'삭제' 버튼을 눌러도 할 일이 안 지워지게, app.js를 살짝 망가뜨려줘.
대신 어떤 부분을 어떻게 망가뜨렸는지는 알려주지 말고 비밀로 해줘.
```

```
● Edit(app.js)
✓ 버그를 심었습니다. (어디를 건드렸는지는 비밀로 하겠습니다.)
  브라우저를 새로고침한 뒤 삭제 기능을 테스트해보세요.
```

**① 재현하기.** 브라우저를 새로고침하고, 할 일을 추가한 뒤 '삭제' 버튼을 눌러보세요. 안 지워집니다. 이때 브라우저의 **개발자 도구**를 열어 에러를 확인합니다. (브라우저 화면에서 **F12** 키를 누르거나 우클릭 → "검사"를 누르면 열립니다. `Console` 탭을 보세요.)

빨간 에러 메시지가 보일 겁니다. 예를 들면 이런 식입니다.

```
Uncaught TypeError: Cannot read properties of undefined (reading 'filter')
    at deleteTodo (app.js:34)
    at HTMLButtonElement.onclick (index.html:1)
```

이 빨간 글씨가 바로 **재현 정보**입니다. 무슨 뜻인지 몰라도 됩니다. **통째로 복사해서 AI에게 넘기면** 됩니다.

**② 진단 + ③ 수정.** Claude Code로 돌아와, 방금 본 에러를 그대로 붙여넣고 요청합니다.

```
'삭제' 버튼을 눌렀더니 할 일이 안 지워지고, 브라우저 콘솔에 이 에러가 떠:

Uncaught TypeError: Cannot read properties of undefined (reading 'filter')
    at deleteTodo (app.js:34)

이 에러의 원인을 찾아서 설명해주고, 고쳐줘.
어떻게 고치는지 변경 내용(diff)도 보여줘.
```

AI는 에러가 가리키는 곳(`app.js:34`)을 읽고 원인을 진단합니다.

```
● Read(app.js)

[원인 진단]
에러는 deleteTodo 함수 34번째 줄에서 발생합니다.
"undefined의 filter를 읽을 수 없다"는 뜻인데, 코드를 보니
삭제할 때 참조하는 변수 이름이 'todos'여야 하는데 'todoList'로
잘못 적혀 있습니다. 'todoList'라는 변수는 존재하지 않아서
undefined가 되고, 거기에 .filter()를 부르니 터진 겁니다.

[수정]
● Edit(app.js)
  function deleteTodo(id) {
-   todos = todoList.filter(todo => todo.id !== id);
+   todos = todos.filter(todo => todo.id !== id);
    saveTodos();
    renderTodos();
  }

존재하지 않는 'todoList'를 올바른 변수 'todos'로 바꿨습니다.
이제 삭제가 정상 동작할 것입니다.
```

코드를 못 읽어도 흐름은 잡힙니다. **이름을 잘못 쓴 변수 하나** 때문에 삭제가 통째로 망가졌고, AI가 그 한 글자 차이를 찾아 바로잡은 겁니다. `-` 줄이 고치기 전, `+` 줄이 고친 후입니다.

**④ 검증.** 가장 중요하고 가장 자주 빠뜨리는 단계입니다. 고쳤다고 끝이 아니라, **정말 고쳐졌는지 직접 확인**해야 합니다.

브라우저를 새로고침하고 다시 '삭제'를 눌러보세요. 이번엔 깔끔히 지워질 겁니다. 콘솔의 빨간 에러도 사라졌습니다.

확인까지 마쳤다면 AI에게 검증을 부탁해 마무리할 수도 있습니다.

```
이제 삭제가 잘 돼. 혹시 이번 수정 때문에 다른 기능
(추가, 완료 표시, 저장)이 깨지지 않았는지 코드를 한 번 점검해줘.
```

```
● Read(app.js)
점검 결과, 이번 수정은 deleteTodo 함수의 변수명만 바로잡은 것이라
추가·완료 표시·저장 기능에는 영향이 없습니다. 안전합니다.
```

> **검증을 빼먹지 마세요.** AI가 "고쳤습니다"라고 말해도, 실제로 동작을 확인하기 전까지는 고쳐진 게 아닙니다. **눈으로 직접 확인**하고, 가능하면 "다른 기능이 깨지지 않았는지 점검해줘"로 한 번 더 안전을 확인하는 습관이 중급의 품질을 만듭니다.

스스로 해보기: 이번엔 AI에게 "'추가' 버튼이 동작하지 않는 버그를 몰래 심어줘"라고 한 뒤, 위 4단계 루프(재현 → 에러 복사 → 진단·수정 → 검증)를 혼자 힘으로 완주해보세요.

## 5.7 CLAUDE.md — 프로젝트 규칙을 AI에게 영구히 기억시키기

지금까지 우리는 매번 요청할 때마다 맥락을 손으로 넣어줬습니다. "CSS만 고쳐줘", "기존 디자인 건드리지 마", "한국어로 설명해줘"처럼요.

그런데 같은 말을 매번 반복하는 건 번거롭습니다. **이 프로젝트에서는 항상 지켜야 하는 규칙**이라면, 한 번 적어두고 AI가 늘 기억하게 하면 좋지 않을까요?

그게 바로 `CLAUDE.md`입니다.

> **CLAUDE.md란?** 프로젝트 폴더에 두는 **AI 전용 안내문**입니다. Claude Code는 작업을 시작할 때 이 파일을 **자동으로 읽고** 거기 적힌 규칙을 늘 염두에 둡니다. 매번 말로 설명하던 맥락을, 파일에 한 번 적어 **영구히 기억**시키는 셈입니다. 새 팀원에게 건네는 "우리 프로젝트 사용 설명서"라고 생각하면 됩니다.

### 실습 5-6: CLAUDE.md 만들고 적용 전후 비교하기

먼저 **CLAUDE.md가 없는 상태**에서 AI가 어떻게 행동하는지 봅시다. `todo-app`에서 이렇게 요청합니다.

```
할 일이 하나도 없을 때 화면에 안내 문구를 띄워줘.
```

```
안내 문구를 추가하겠습니다.

● Edit(app.js)
● Edit(style.css)
✓ 완료. "No todos yet. Add one above!" 라는 영어 안내 문구를
  회색 글씨로 추가했습니다.
```

영어로 문구를 넣었네요. 우리 앱은 한국어인데 말이죠. 또 어떤 스타일로 넣을지도 AI 마음대로였습니다. 매번 "한국어로 해줘", "기존 색감에 맞춰줘"라고 말해야 한다는 뜻입니다.

이제 **규칙을 영구화**해 봅시다. AI에게 직접 `CLAUDE.md`를 만들게 하겠습니다.

```
이 프로젝트 루트에 CLAUDE.md 파일을 만들어줘. 다음 규칙을 담아줘:
- 모든 사용자용 문구(버튼·안내·메시지)는 한국어로 작성한다
- 새 디자인은 기존 style.css의 색·폰트·여백 톤에 맞춘다
- 큰 변경(파일 2개 이상 수정)은 실행 전에 계획부터 보여준다
- 변수·함수 이름은 기존 코드의 영어 캐멀케이스 방식을 따른다
- 작업 후에는 무엇을 왜 바꿨는지 한국어로 한 줄 요약한다
```

AI가 파일을 만들어줍니다. 실제로 생성되는 `CLAUDE.md`는 이렇게 짧고 명확합니다.

```markdown
# CLAUDE.md

## 프로젝트
브라우저 localStorage로 동작하는 순수 HTML/CSS/JS 할 일 목록 앱.

## 작업 규칙
1. 모든 사용자용 문구(버튼·안내·메시지)는 한국어로 작성한다.
2. 새 디자인은 기존 style.css의 색·폰트·여백 톤에 맞춘다.
3. 큰 변경(파일 2개 이상 수정)은 실행 전에 계획부터 보여준다.
4. 변수·함수 이름은 기존 코드의 영어 캐멀케이스 방식을 따른다.
5. 작업 후에는 무엇을 왜 바꿨는지 한국어로 한 줄 요약한다.
```

> **딱 5줄짜리 규칙이면 충분합니다.** CLAUDE.md는 길어야 좋은 게 아닙니다. 정말 중요한 규칙 몇 줄이 백 줄짜리 장황한 문서보다 훨씬 잘 지켜집니다. 처음엔 짧게 시작하고, 같은 잔소리를 반복하는 자신을 발견할 때마다 한 줄씩 추가하세요.

이제 **CLAUDE.md가 있는 상태**에서 똑같은 요청을 다시 해봅니다. (방금 영어로 넣은 문구는 먼저 되돌려달라고 한 뒤 진행하세요.)

```
할 일이 하나도 없을 때 화면에 안내 문구를 띄워줘.
```

```
CLAUDE.md 규칙을 확인했습니다. (한국어 문구, 기존 디자인 톤 유지)

● Edit(app.js)
● Edit(style.css)
✓ 완료. "아직 할 일이 없어요. 위에서 하나 추가해보세요!" 라는
  한국어 안내 문구를, 기존 style.css의 회색 톤(#9ca3af)과
  같은 폰트 크기에 맞춰 추가했습니다.

[요약] 빈 목록일 때 한국어 안내 문구를 기존 디자인 톤에 맞춰 표시.
```

차이가 분명하죠?

| | CLAUDE.md 없을 때 | CLAUDE.md 있을 때 |
|--|------------------|------------------|
| 문구 언어 | 영어 (제멋대로) | 한국어 (규칙대로) |
| 디자인 | AI 임의 선택 | 기존 톤에 맞춤 |
| 작업 요약 | 없음 | 한국어 한 줄 요약 |
| 내 수고 | 매번 말로 설명 | 한 번 적고 끝 |

이것이 CLAUDE.md의 힘입니다. **맥락을 말로 반복하는 대신 파일로 영구화**하면, AI는 매번 같은 규칙 위에서 일관되게 움직입니다. 그리고 이 파일은 단순한 메모가 아닙니다. 나중에 챕터 8에서 보겠지만, 이 `CLAUDE.md`를 **팀 저장소에 올려 공유**하면 팀원 모두의 AI가 똑같은 규칙으로 일하게 됩니다.

스스로 해보기: 여러분의 `CLAUDE.md`에 "절대 localStorage 저장 방식을 다른 방식으로 바꾸지 말 것"이라는 규칙을 한 줄 추가해보세요. 그런 다음 "저장 방식을 다른 걸로 바꿔줘"라고 요청해, AI가 그 규칙을 어떻게 존중하며 반응하는지 관찰해보세요.

## 5.8 중급 작업의 안전 수칙 정리

이 챕터에서 흩어져 나온 안전 원칙들을 한자리에 모읍니다. 큰 코드를 다룰 때 이 다섯 줄만 기억하면, 사고 없이 AI에게 일을 맡길 수 있습니다.

```
1. 고치기 전에 파악하라      "이 프로젝트 설명해줘"로 전체 그림부터
2. 구체적인 단어를 줘라       AI는 그 단어로 검색해 길을 찾는다
3. 큰 변경은 계획부터 받아라   "계획부터 보여줘" → 승인 → 실행
4. 작은 단위로 쪼개 승인하라   "1단계만 하고 멈춰줘"로 위험을 줄인다
5. 고친 뒤 반드시 검증하라     "고쳤습니다"는 확인 전엔 완료가 아니다
```

여기에 더해, 반복되는 규칙은 **CLAUDE.md에 적어 영구화**하면 매번 말할 필요가 사라집니다. 이 여섯 가지가 "AI를 쓰는 사람"과 "AI를 잘 다루는 사람"을 가르는 차이입니다.

## 이 챕터에서 배운 것

- 중급의 무대는 "내가 만든 작은 결과물"에서 "남이 만든 큰 코드"로 바뀐다 — 핵심 실력은 **맥락을 주는 능력**이다
- 처음 보는 프로젝트는 고치기 전에 **"이 프로젝트 설명해줘"**로 전체 구조부터 파악시킨다
- AI는 우리가 준 단어로 **코드를 검색**해 관련 파일을 스스로 찾는다 — 그래서 구체적인 단어가 곧 정확한 결과로 이어진다
- 파일 두 개 이상을 건드릴 큰 변경은 **Plan(계획)을 먼저 받고**, 승인한 뒤 실행한다 (Shift+Tab 또는 "계획부터 보여줘")
- 큰 작업은 **작은 단위로 쪼개 단계별로 승인**하면 안전하다
- 버그는 **재현 → 진단 → 수정 → 검증**의 4단계 루프로 잡는다 — 에러 메시지는 AI에게 주는 가장 값진 단서다
- 고친 뒤에는 **반드시 직접 검증**하고, 다른 기능이 깨지지 않았는지 점검한다
- **CLAUDE.md**에 프로젝트 규칙을 5줄로 적어두면, AI가 매번 그 규칙을 자동으로 기억하고 일관되게 따른다
